## 5. ルーム生成と対象識別

1. Bot以外のユーザーが設定親VCへ入った場合のみ起動する。同じVC内のミュート変更などは無視。
2. 作成前に現在地と設定を再確認し、参加者単位の多重作成を防ぐ。
3. 設定カテゴリに子VCを作成し、そのIDと生成元を永続保存する。
4. 保存成功後、まだ親VCにいるユーザーを子VCへ移動する。
5. 実際の子VC在室を確認してロール同期する。親VC参加だけでは付与しない。

対象判定の根拠は永続生成記録。カテゴリ名・ルーム名・同じカテゴリという条件だけでは認定しない。手動VC、親VC、他Bot生成VCを取り込まない。再起動時も同じ記録から識別する。

既存direct生成処理にはグループ分け用の命名・人数制限があるため、その処理全体の流用はしない。共通化可能な作成・移動・例外処理だけを小さく再利用する。

作成成功後のDB保存失敗、移動失敗、参加者の先行退出は個別に扱う。確実に今回生成した空VCだけを補償削除候補にし、参加者がいるVCを削除しない。作成結果不明時に推測で既存VCを取り込んだり再生成を連打したりしない。

## 6. ready・成立判定

| イベント | 動作 |
| --- | --- |
| ready押下 | Bot・現在地・有効ルーム・有効パネルを確認。未登録なら現在ルームのSetに追加 |
| 重複ready | Setは変更せず指示書の重複受付文をEphemeralで返す |
| 1人でready | 登録維持。指示書の1人用文を返す。成立させない |
| 新規参加 | 既存readyは維持。参加者本人だけ未ready |
| キャンセル | 現在のルームの本人だけ解除。未登録・対象外もEphemeral |
| 退出・別VC移動 | 元ルームの本人だけ即時解除。元ルームを5秒後に再判定 |
| RTC間移動 | 移動先では未ready。利用中ロールは維持 |
| ルーム削除 | 当該readyとタイマーを破棄し、関係メンバーの現在地からロール再確認 |

返信とパネル文は原資料の指定文を使用する。ready人数・未ready者・押下者をパネル、公開返信、運用CHログに載せない。

### 5秒待機と同時操作

退出イベントごとに5秒後の判定機会を確保し、最新の退出から5秒間は退出を原因とする成立を確定しない。先行タイマーが新たな退出直後に成立させないよう期限も確認する。待機中のready押下も登録自体は受け付け、退出による人数減少を即時成立の抜け道にしない方針。

ルームごとにready・キャンセル・退出処理と成立処理を直列化する。ロック待ち後、Discord操作の直前にも在室状況を再確認する。通知処理中の押下や古いタイマーは受付世代で区別し、次回分のreadyを消さない。これは重複処理の防止であり、利用者へのクールダウンは設けない。

5秒後はイベント当時の参加者一覧を使わず、その時点のGateway由来のVC参加状態で判定する。チャンネルの取得成功だけを参加者情報の完全性の根拠にしない。切断中・復旧未完了で状態が不明なら通知を保留する。

### 成立処理

1. Bot以外の現在参加者を再取得。
2. 2人以上、全員ready、退出待機期限経過、ルーム有効を最終確認。
3. 当該VCのテキストチャットに、対象者の個別メンションと指定文を送る。ロールメンションは使用しない。
4. 送信成功後だけ、その受付回のreadyを全解除。

送信が明確に失敗したらreadyを保持して例外を隔離する。送信結果不明の場合は直ちに同文を再送せず、当該通知の確認・重複回避方針を設ける。Discord送信とメモリ状態を原子的には更新できない点は障害系テストに含める。

移動先は `getVoiceReminderParentChannelIds(settings)` から取得し、有効なVCをチャンネルメンションで表示する。0件なら移動手順だけ省略。1件・2件は指定文どおり。独立した移動先設定を新設しない。

## 7. ロール同期・パネル・設定変更

### ロール

現在の対象VC在室を正とする。1人でも付与し、通常VCまたは未接続なら解除。RTC間の移動では解除・再付与を行わない。メンバー別キューで移動直後の古いロール処理を防ぐ。

起動時は設定適用が落ち着いた後、ルーム記録を復元してから、現在のRTC参加者とロール保持者の両方を確認する。メンバーキャッシュだけで全保持者を把握したと判断せず、必要なメンバー取得と利用可能なIntentを検証する。取得失敗を「不在」に置き換えて一括解除しない。Botは対象外。

### パネル

保存IDのメッセージを検証して再利用し、必要なら内容更新。確実に不存在の場合だけ新規作成。記録喪失時はBot自身とRTC customIdを照合して回収し、履歴の1ページにないだけで不存在とは判定しない。権限不足・通信障害では追加投稿しない。

リースまたは既存の同等排他で起動・設定適用の同時作成を防ぐ。ボタンは設定CHと有効メッセージIDにも照合し、古いパネルを無効化する。旧CHの後始末が失敗しても有効パネルは1件に限定する。

### 設定変更

適用ジョブにRTC区分を追加し、変更前後の値で処理する。受付CH変更は旧パネル停止→新パネル確保。ロール変更は旧ロール解除と新ロール同期を行う。RTC親・カテゴリ変更時は、新規生成先だけを切り替え、既存生成ルームは在室者を追い出さず記録で管理し続ける案とする。通常の部分更新で既存readyを一律消去しない。

## 8. 未確定点と推奨案

これらは原資料に明記がないため、実装前に仕様として確定する。計画策定はこの確認待ちで止めない。

| 論点 | 推奨する案 |
| --- | --- |
| 空ルームの寿命 | Bot生成記録があり、Botを含め完全に空のルームのみ自動削除。削除直前に再確認。Botだけ残る場合の切断・削除は追加判断事項 |
| 受付CHの閲覧権限 | 運営側で設定する前提。Botは設定チェックと案内を行う。権限の自動書換えは明示要件ではないため初版に含めない |
| 親VCが3〜5件設定済み | 現行コードは最大5件対応。既存ヘルパーが返す有効親VCをすべて表示し、先頭2件へ黙って切り捨てない |
| 命名・番号 | `💬｜チャットルーム-N`。既存の同名VCを対象認定せず、番号の衝突だけ回避する |
| マイク・発話制限 | 指示書に強制ミュート等はないため、新たな発話制限は追加しない |
| 退出待機中のボタンで全員ready | 退出から5秒という要件を優先し、待機期限まで成立通知を保留する |
| 複数Botプロセス | readyをメモリ管理する初版は、各guildを1つのプロセスが担当する運用を前提とする。冗長同時処理をするなら別途共有状態が必要 |

原資料のテストケース3は、そのまま「A/Bのみで両者ready」とするとC参加前に成立・リセットする。再現テストは「Cが在室する中でA/Bがready」または退出待機中の新規参加として構成し、既存readyが新規参加だけで失われないことを確認する。

## 10. 検証計画と完了条件

### 自動テスト

原資料36節の14ケースを網羅する。時間は偽時計で進め、退出後4,999msでは不成立、5,000ms以降に現在参加者で判定することを確認する。

追加ケース:

- 同カテゴリの手動VC・親VC・他Bot生成VCは対象外。
- Botを人数、ready、ロール操作に含めない。
- 戻ってきた退出者のreadyは復活しない。新規参加は既存readyを消さない。
- 連続退出、同時押下、キャンセル競合、通知中の再登録、古いタイマーで二重通知・次回ready消去が起きない。
- パネル再利用・記録喪失回収・権限不足・旧パネル拒否・同時初期化。
- ロール付与失敗、解除失敗、メンバー退出、VC削除、MongoDB不通、通知失敗でBot全体を停止しない。
- 設定変更・リビジョン適用・ロール差替え・再起動で状態が整合する。
- 公開出力にreadyの人数・個人が成立前に漏れない。
- 通常のVC作成・削除・参加ロール・集合フォーム・既存パネル・起動終了ルーターが従来どおり動く。
